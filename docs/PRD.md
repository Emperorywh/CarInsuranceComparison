# 车险报价智能对比工具 PRD

## 1. 产品名称

暂定：

**车险报价对比助手**

产品定位：

> 将不同保险公司、不同保险员、不同格式的车险报价单自动转换成统一结构，让用户能够真正按照“价格、保障、附加险、增值服务、额外保障包”进行横向对比。

核心宣传语可以概括为：

**把保险员发来的报价都丢进来，一眼看懂区别。**

---

# 2. 项目背景

车主进行车险续保时，通常会同时联系多家保险公司以及多个保险员。

实际场景往往是：

```text
人保保险员 A → 报价方案 1
人保保险员 A → 报价方案 2

平安保险员 B → 报价方案 1
平安保险员 B → 报价方案 2
平安保险员 C → 报价方案 3

其他保险公司……
```

用户最后可能收到十几份甚至几十份报价。

问题并不是没有报价，而是：

> 报价太多，而且完全无法直接比较。

从实际报价单来看，不同保险公司的格式、字段和产品结构差异非常明显。

例如人保可能写：

```text
新能源汽车车损失保险

新能源汽车第三者责任保险

新能源汽车车上人员责任保险（司机）

新能源汽车车上人员责任保险（乘客）

附加医保外医疗费用责任险
（新能源汽车第三者责任保险）
```

平安则可能写：

```text
新能源汽车损失保险

新能源汽车第三者责任保险

车上人员责任险：驾驶员

车上人员责任险：乘客

附加医保外医疗费用责任险（第三者）
```

虽然表达不同，但本质上可能是同一类保障。

除此之外，实际报价还存在大量更复杂的数据。

例如：

- 道路救援 2 次
- 车辆安全检测 1 次
- 代驾 2 次
- 代办送检 1 次
- 途顺家安组合保险
- 驾乘人员补充综合保险
- 平安车主尊享保障
- 驾乘意外伤害
- 自费医疗
- 节假日翻倍
- 家庭财产保障
- 行李物品损失
- 个人出行不便保障

这些项目不能简单地全部放进“车险险种”里面进行比较。

因此产品真正需要解决的问题是：

# 将不同保险公司的“报价体系”进行结构化和语义归一化。

---

# 3. 产品核心目标

产品第一阶段核心解决四个问题。

## 3.1 报价单看不懂

将复杂的保险报价单转换成普通用户能够理解的数据。

例如：

```text
新能源汽车第三者责任保险
保险金额：3000000
```

转换为：

```text
三者险
300 万
```

---

## 3.2 不同公司的名称不同

例如：

```text
新能源汽车第三者责任保险

新能源汽车车第三者责任保险

机动车第三者责任保险

第三者责任险

商业第三者责任险

三者险
```

全部归一化：

```text
第三者责任险
```

---

## 3.3 不同报价保障结构不同

不能只比较总价格。

例如：

```text
方案 A
¥5,420

三者险 200 万
医保外三者险 100 万
```

另外一个方案：

```text
方案 B
¥5,785

三者险 300 万
医保外三者险 50 万
额外驾乘保障
```

系统需要告诉用户：

> B 并不是单纯比 A 贵 365 元。

而是：

> B 的三者险增加了 100 万，同时医保外三者险减少了 50 万，并增加了一份额外驾乘保障。

---

## 3.4 官方报价和保险员营销方案混在一起

从实际报价中可以看到大量红色文字、箭头以及保险员额外标注，例如：

```text
驾乘险 60 万

三者医保外 50 万

自费医疗

节假日 90 万

100%赔付
```

这些内容不能直接当作正式保单字段。

系统必须区分：

```text
保险公司正式报价

VS

保险员补充说明

VS

系统识别结果

VS

用户自己填写的信息
```

```text

```

结构：

```text
用户
 │
 └── 对比项目

       ├── 报价方案 1
```

**同一辆车的一次续保周期。**


# 8. 报价方案与文件不能完全等价

这是根据真实报价必须增加的设计。

不能简单定义：

```text
1 个文件 = 1 个报价
```

因为未来可能出现：

```text
报价单第 1 页
报价单第 2 页
保险员补充截图
优惠说明截图
```

全部属于同一个报价方案。

因此数据关系应该为：

```text
Quote
 ├── QuoteFile
 ├── QuoteFile
 └── QuoteFile
```

即：

# 一个报价方案可以包含多个文件。

---

# 9. 报价版本管理

实际场景中同一个保险员会连续修改方案。

例如：

```text
平安方案 A

三者险：
200 万
```

随后：

```text
平安方案 B

三者险：
300 万
```

然后：

```text
平安方案 C

三者险：
300 万
+
驾乘保障
```

系统不应该认为这三个完全没有关系。

应该支持：

```text
保险公司：平安

报价来源：保险员 A

方案 A
方案 B
方案 C
```

并能够自动提示：

> 这是同一保险公司的不同报价版本。

---

# 10. 报价数据必须分层

真实报价不能只有一个 InsuranceItem 表。

至少需要分为以下五层。

```text
报价方案

├── ① 基础车险
│
├── ② 附加险
│
├── ③ 增值服务
│
├── ④ 独立保障包
│
└── ⑤ 销售优惠 / 补充说明
```

这是整个数据模型最重要的设计原则。

---

# 11. 第一层：基础车险

统一归一化以下核心险种。

## 11.1 交强险

标准字段：

```text
是否包含

保费

保险期间
```

---

## 11.2 车损险

原始名称可能为：

```text
新能源汽车车损失保险

新能源汽车损失保险

机动车损失保险

车损险
```

统一：

# 车损险

字段：

```text
是否投保

保险金额

保费
```

例如实际报价中可能出现：

```text
147719.12 元
```

或者：

```text
138618.67 元
```

或者：

```text
131009.56 元
```

必须保存真实数值。

不能因为是同一辆车，就认为所有报价的车损险保险金额一定一样。

---

# 12. 第三者责任险

统一：

# 三者险

字段：

```text
是否投保

保险金额

保费
```

实际报价可能存在：

```text
200 万

300 万

500 万
```

内部统一存储：

```text
2000000
3000000
5000000
```

展示层：

```text
200 万
300 万
500 万
```

# 13. 车上人员责任险

必须拆成：

## 驾驶员

字段：

```text
保额

保费
```

例如：

```text
0.1 万

10000 元
```

统一：

```text
10000
```

---

## 乘客

需要额外保存：

```text
单座保额

座位数

总保额

保费
```

例如：

```text
0.1 万 / 座 × 4

或者：

4 座 × 10000 元
```

统一：

```text
单座：
10000

座位：
4

总保额：
40000
```

# 14. 第二层：附加险

真实报价中已经出现多个重要附加险。

---

## 14.1 医保外医疗费用责任险

不能只定义一个：

```text
医保外用药险
```

必须区分保障对象。

至少包含：

### 第三者医保外

```text
THIRD_PARTY_NON_MEDICAL_INSURANCE
```

### 驾驶员医保外

```text
DRIVER_NON_MEDICAL_INSURANCE
```

### 乘客医保外

```text
PASSENGER_NON_MEDICAL_INSURANCE
```

字段：

```text
保险金额

保费

是否共享保额
```

例如实际报价中存在：

```text
30 万

50 万

100 万
```

因此必须可以独立进行比较。

# 15. 外部电网故障损失险

新能源汽车报价中已经出现：

```text
附加外部电网故障损失险
```

需要作为标准附加险维护。

字段：

```text
是否包含

保险金额

保费
```

# 16. 第三层：免费增值服务

不能把：

```text
道路救援
```

当作传统意义上的保险险种。

应该建立：

# ServiceBenefit

统一保存。

目前实际样例已经出现：

```text
道路救援

车辆安全检测

代为驾驶

代为送检
```

字段：

```text
服务类型

服务次数

费用

原始描述
```

例如：

```text
道路救援
2 次
0 元
```

---

# 17. 增值服务详细描述

部分报价单会提供非常长的服务说明。

例如车辆安全检测可能包含：

```text
发动机检测

变速器检测

转向系统检测

底盘检测

轮胎检测

汽车玻璃检测

汽车电子系统检测

车内环境检测
```

第一阶段不需要把这些全部拆成独立字段。

可以保存为：

```text
serviceType

count

description
```

后期再逐渐结构化。

---

# 18. 第四层：独立保障包

这是根据真实报价增加的最重要模块之一。

实际报价中已经出现：

### 人保

```text
途顺家安组合保险

驾乘人员补充综合保险
```

### 平安

```text
平安车主尊享保障
```

这些产品：

**不能与商业车险直接混在一个险种表中。**

原因是它们本质上可能属于：

- 驾乘意外险
- 意外医疗险
- 家财险
- 交通意外险
- 出行保障
- 综合保障产品

因此定义：

# SupplementalPackage

例如：

```text
平安车主尊享保障

价格：
348 元
```

下面再包含：

```text
PackageCoverage[]
```

---

# 19. 独立保障包内部保障

实际报价已经出现：

```text
驾乘意外身故及残疾

驾乘意外医疗

自费医疗

飞机意外

火车意外

轮船意外

汽车意外

救护车费用

个人出行不便

家庭财产保障
```

因此数据应该设计为：

```text
SupplementalPackage

├── Coverage
├── Coverage
├── Coverage
└── Coverage
```

而不是将整包只存成一句：

```text
驾乘险 60 万
```

---

# 20. 特殊保障规则

实际保险方案中还存在：

```text
法定节假日翻倍

每座金额

共享保额

指定人员

不限人员

每次限额
```

因此 Coverage 不能只保存：

```text
amount
```

至少需要：

```text
amount

unit

perSeat

seatCount

shared

multiplier

condition

description
```

例如：

```text
基本保障：
30 万

法定节假日：
翻倍

最终节假日保障：
60 万
```

应该结构化为：

```text
amount = 300000

multiplier = 2

condition = LEGAL_HOLIDAY
```

---

# 21. 第五层：保险员补充信息

实际报价截图中存在大量：

```text
红色文字

箭头

方框

手写标注

额外宣传语
```

这些内容必须单独处理。

系统需要识别：

```text
PRINTED_OFFICIAL

SALES_ANNOTATION

USER_ANNOTATION
```

即：

### 正式保险公司内容

和：

### 保险员标注内容

不能混为一谈。

---

# 22. 销售说明识别规则

例如报价图片上出现：

```text
驾乘险 60 万

医保外 50 万

自费医疗

100%赔付
```

系统可以识别出来，但默认状态应该是：

```text
销售补充说明
```

而不是：

```text
正式保险责任
```

UI 中应该明显提示：

> 此信息来自图片附加标注，并非报价单正式表格内容，请用户确认。

---

# 23. 价格必须重新设计

实际报价证明：

一个简单的：

```text
totalPrice
```

远远不够。

至少需要：

```text
商业险保费

交强险

车船税

额外保障包

其他费用

官方报价总额

优惠

返现

礼品折现金额

最终实付金额
```

---

# 24. 官方报价总价

例如：

```text
商业险
4392.14

交强险
1045

车船税
0

车主保障
348
```

则：

```text
官方总价：

5785.14
```

系统应该自动重新计算一次。

如果：

```text
系统计算金额
≠
报价单显示金额
```

则显示：

> 金额存在异常，请确认。

---

# 25. 实际成交价

真实保险销售场景中经常存在：

```text
报价 6000

返现 500

微信红包 200

购物卡 100
```

最终真实成本：

```text
5200
```

而这些通常不会出现在正式报价单。

因此报价页面必须允许用户填写：

```text
现金返现

优惠券

红包

购物卡

油卡

其他优惠
```

并计算：

# 实际净支出

公式：

```text
实际净支出
=
官方报价
-
现金返现
-
可折现优惠
+
额外费用
```

---

# 26. 优惠不能全部简单减钱

例如：

```text
洗车 5 次

保养一次

道路救援

购物卡 200
```

其中：

```text
购物卡
```

可以允许用户填写估值。

但是：

```text
道路救援
```

默认不能直接按照某个金额扣减。

所以权益存在：

```text
cashEquivalent
```

用户可以自己选择是否估值。

---

# 27. 报价单状态值不能简单使用 0

实际报价中存在：

```text
0.00

—

空白

不存在此项目
```

它们的含义可能完全不同。

因此需要状态：

```text
INCLUDED

NOT_INCLUDED

FREE

NOT_APPLICABLE

UNKNOWN
```

例如：

```text
道路救援
2 次
0 元
```

代表：

```text
FREE
```

而不是：

```text
NOT_INCLUDED
```

---

# 28. 原始数据必须永久保留

每一个字段至少保存：

```text
rawName

rawValue

normalizedName

normalizedValue
```

例如：

```json
{
  "rawName": "新能源汽车车第三者责任保险",
  "rawValue": "300万元",
  "normalizedCode": "THIRD_PARTY_LIABILITY",
  "normalizedAmount": 3000000
}
```

这样未来解析算法升级之后，可以重新处理历史报价。

---

# 29. 字段来源定位

每个识别字段建议同时保存：

```text
文件

页码

OCR Bounding Box

原始文字
```

最终用户点击：

```text
三者险
300 万
```

可以：

# 定位到原报价单位置

甚至直接框选：

```text
新能源汽车第三者责任保险
300万元
```

这会极大提高产品可信度。

---

# 30. OCR 置信度

每一个自动提取字段保存：

```text
confidence
```

例如：

```text
保险公司：
99%

三者险：
98%

三者保额：
97%

保障包：
82%

销售员标注：
65%
```

低置信度数据需要：

### 黄色提醒。

严重不确定：

### 红色提醒。

# 32. 信息分类

识别结果建议分 Tab：

```text
价格

基础车险

附加险

额外保障
```

# 47. AI 推荐必须谨慎

产品定位建议为：

# 决策辅助

而不是：

# AI 替用户买保险

所以 AI 不应该简单回答：

```text
你应该买方案 A。
```

应该回答：

```text
如果你最关注总价格，
A 成本最低。

如果你希望三者险达到 300 万，
B 和 C 满足条件。

如果你更关注医保外第三者保障，
A 的额度更高。

如果你希望同时拥有额外驾乘保障，
C 包含独立保障包。
```

最终决定交给用户。


例如：

```text

```

必须转换：

```text

```

例如：


```text

seatCount = 4
```

## 重复险种校验

被 OCR 两次。

```text

```

则不能错误覆盖：

```text

1 万
```

这两个保障完全不是同一个东西。

# 70. 最重要的产品调整

结合实际报价以后，这个产品不应该定义成：

> OCR 识别车险报价然后做表格。

正确的产品定义应该是：

# 多保险公司车险报价标准化与决策辅助系统

它实际上做的是：

```text
不同保险公司的报价语言
            ↓
统一保险数据语言
            ↓
形成真正可比较的数据
```

整个系统最核心的三个引擎分别是：

```text
① Quote Parser
报价解析引擎

② Insurance Normalization Engine
保险字段归一化引擎

③ Comparison Engine
报价比较引擎
```

以后增加：

```text
④ Insurance Analysis Agent
保险分析 Agent
```

形成：

```text
报价单
  ↓
Parser
  ↓
Normalization
  ↓
Comparison
  ↓
AI Agent
```

这会比单纯做一个“上传图片 → GPT 分析”的产品稳定得多，也更容易形成长期技术和数据壁垒。

# 71. 第一版成功标准

MVP 不需要做到所有保险公司的所有险种都能识别。

第一阶段可以先要求：

### 人保 + 平安

两家公司支持度最高。

针对真实车险报价，至少做到：

- 核心险种识别准确；
- 三者 200 万 / 300 万能够正确区别；
- 司机、乘客责任险不会混淆；
- 医保外第三者 / 驾驶员 / 乘客不会混淆；
- 独立驾乘保障不会错误归类为车上人员责任险；
- 0 元服务能够识别为“免费”，而不是“不包含”；
- 额外保障包能够独立计算价格；
- 官方总价能够自动校验；
- 红色文字、箭头等销售员备注不会自动污染正式保单数据；
- 用户能够修改任何 AI 识别错误的数据；
- 任意两个方案能够快速看到价格和保障差异。

如果这十项能够稳定做到，这个产品的 MVP 已经具备非常明确的实际使用价值。
