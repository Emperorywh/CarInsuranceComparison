# 车险报价智能对比工具 PRD

## 1. 产品名称

暂定：

**车险报价对比助手**

产品定位：

> 将不同保险公司、不同保险员、不同格式的车险报价单自动转换成统一结构，让用户能够真正按照“价格、保障、附加险、增值服务、额外保障包”进行横向对比。

文档分工：本文描述产品目标和业务边界；MVP 的具体数据结构、状态机、接口和验收口径以 `docs/SPEC_MVP.md` 为实现依据。两份文档如有冲突，必须记录决策并同步修订，不能静默覆盖。

核心宣传语可以概括为：

**把保险员发来的报价都丢进来，一眼看懂区别。**

---

# 2. 项目背景

车主进行车险续保时，通常会同时联系多家保险公司以及多个保险员。

实际场景往往是：

```text
人保保险员 A → 报价方案 1
人保保险员 A → 报价方案 2

平安保险员 B → 报价方案 1
平安保险员 B → 报价方案 2
平安保险员 C → 报价方案 3

其他保险公司……
```

用户最后可能收到十几份甚至几十份报价。

问题并不是没有报价，而是：

> 报价太多，而且完全无法直接比较。

从实际报价单来看，不同保险公司的格式、字段和产品结构差异非常明显。

例如人保可能写：

```text
新能源汽车车损失保险

新能源汽车第三者责任保险

新能源汽车车上人员责任保险（司机）

新能源汽车车上人员责任保险（乘客）

附加医保外医疗费用责任险
（新能源汽车第三者责任保险）
```

平安则可能写：

```text
新能源汽车损失保险

新能源汽车第三者责任保险

车上人员责任险：驾驶员

车上人员责任险：乘客

附加医保外医疗费用责任险（第三者）
```

虽然表达不同，但本质上可能是同一类保障。

除此之外，实际报价还存在大量更复杂的数据。

例如：

- 道路救援 2 次
- 车辆安全检测 1 次
- 代驾 2 次
- 代办送检 1 次
- 途顺家安组合保险
- 驾乘人员补充综合保险
- 平安车主尊享保障
- 驾乘意外伤害
- 自费医疗
- 节假日翻倍
- 家庭财产保障
- 行李物品损失
- 个人出行不便保障

这些项目不能简单地全部放进“车险险种”里面进行比较。

因此产品真正需要解决的问题是：

# 将不同保险公司的“报价体系”进行结构化和语义归一化。

---

# 3. 产品核心目标

产品第一阶段核心解决四个问题。

## 3.1 报价单看不懂

将复杂的保险报价单转换成普通用户能够理解的数据。

例如：

```text
新能源汽车第三者责任保险
保险金额：3000000
```

转换为：

```text
三者险
300 万
```

---

## 3.2 不同公司的名称不同

例如：

```text
新能源汽车第三者责任保险

新能源汽车车第三者责任保险

机动车第三者责任保险

第三者责任险

商业第三者责任险

三者险
```

全部归一化：

```text
第三者责任险
```

---

## 3.3 不同报价保障结构不同

不能只比较总价格。

例如：

```text
方案 A
¥5,420

三者险 200 万
医保外三者险 100 万
```

另外一个方案：

```text
方案 B
¥5,785

三者险 300 万
医保外三者险 50 万
额外驾乘保障
```

系统需要告诉用户：

> B 并不是单纯比 A 贵 365 元。

而是：

> B 的三者险增加了 100 万，同时医保外三者险减少了 50 万，并增加了一份额外驾乘保障。

---

## 3.4 官方报价和保险员营销方案混在一起

从实际报价中可以看到大量红色文字、箭头以及保险员额外标注，例如：

```text
驾乘险 60 万

三者医保外 50 万

自费医疗

节假日 90 万

100%赔付
```

这些内容不能直接当作正式保单字段。

系统必须区分：

```text
保险公司正式报价

VS

保险员补充说明

VS

系统识别结果

VS

用户自己填写的信息
```

# 4. 产品核心对象

整个产品围绕：

# 对比项目

展开。

例如：

```text
2026 年车辆续保
```

结构：

```text
用户
 │
 └── 对比项目
       │
       ├── 报价方案 1
       │     └── 原始报价单
       │
       ├── 报价方案 2
       │     └── 原始报价单
       │
       └── 报价方案 3
             └── 原始报价单
```

一个项目通常对应：

**同一辆车的一次续保周期。**

# 5. 用户核心流程

完整流程：

```text
新建续保对比项目
        ↓
创建报价并选择保险公司
        ↓
上传报价单
        ↓
视觉模型 / 文档解析
        ↓
识别并核对保险公司
        ↓
识别车辆信息
        ↓
识别保险项目
        ↓
识别额外保障包
        ↓
识别增值服务
        ↓
识别报价金额
        ↓
标准化字段
        ↓
数据校验
        ↓
用户确认
        ↓
加入对比
        ↓
多方案横向比较
        ↓
差异分析
        ↓
AI 辅助解释（第二阶段）
```

# 6. 新建对比项目

用户点击：

**新建车险对比**

填写：

```text
项目名称

车辆名称

续保年份

保险到期时间（可选）

备注
```

例如：

```text
2026 年车辆续保
```

车辆详细信息原则上不要求用户手动填写。

后续通过报价单自动获取。

每份报价仍要保留自己的车辆信息快照。后续报价与项目车辆摘要的车型、座位数或新能源属性不一致时，系统必须提示用户确认，避免把不同车辆的报价放进同一项目比较。

---

# 7. 上传报价单

支持：

- JPG
- JPEG
- PNG
- PDF

后续支持：

- Excel
- Word
- 微信聊天截图

支持：

```text
单文件上传

多文件批量上传

拖拽上传
```

MVP 采用“先创建报价、再上传文件”：用户先选择保险公司并可填写保险员称呼，系统解析后再次识别公司；两者不一致时必须由用户确认。

首次调用视觉模型前，页面必须明确说明原始文件会发送至当前配置的模型供应商进行解析。用户不同意时，可以改用完整手动录入。

# 8. 报价方案与文件不能完全等价

这是根据真实报价必须增加的设计。

不能简单定义：

```text
1 个文件 = 1 个报价
```

因为未来可能出现：

```text
报价单第 1 页
报价单第 2 页
保险员补充截图
优惠说明截图
```

全部属于同一个报价方案。

因此数据关系应该为：

```text
Quote ── QuoteFileLink ── QuoteFile
```

即：

# 一个报价方案可以包含多个文件。

同一张包含多个方案的原文件，也可以由拆分后的多个报价方案共享。文件属于对比项目，不由某一个子报价独占。

---

# 9. 报价版本管理

实际场景中同一个保险员会连续修改方案。

例如：

```text
平安方案 A

三者险：
200 万
```

随后：

```text
平安方案 B

三者险：
300 万
```

然后：

```text
平安方案 C

三者险：
300 万
+
驾乘保障
```

系统不应该认为这三个完全没有关系。

应该支持：

```text
保险公司：平安

报价来源：保险员 A

方案 A
方案 B
方案 C
```

并能够自动提示：

> 这是同一保险公司的不同报价版本。

MVP 不建立完整 QuoteVersion 版本链。第一版将这些方案作为平级 Quote，按照“保险公司 + 保险员”分组展示并提示同来源；正式版本链留到第二阶段。

---

# 10. 报价数据必须分层

真实报价不能只有一个 InsuranceItem 表。

至少需要分为以下五层。

```text
报价方案

├── ① 基础车险
│
├── ② 附加险
│
├── ③ 增值服务
│
├── ④ 独立保障包
│
└── ⑤ 销售优惠 / 补充说明
```

这是整个数据模型最重要的设计原则。

---

# 11. 第一层：基础车险

统一归一化以下核心险种。

## 11.1 交强险

标准字段：

```text
是否包含

保费

保险期间（MVP 在原文件中保留，暂不结构化比较）
```

---

## 11.2 车损险

原始名称可能为：

```text
新能源汽车车损失保险

新能源汽车损失保险

机动车损失保险

车损险
```

统一：

# 车损险

字段：

```text
是否投保

保险金额

保费
```

例如实际报价中可能出现：

```text
147719.12 元
```

或者：

```text
138618.67 元
```

或者：

```text
131009.56 元
```

必须保存真实数值。

不能因为是同一辆车，就认为所有报价的车损险保险金额一定一样。

---

# 12. 第三者责任险

统一：

# 三者险

字段：

```text
是否投保

保险金额

保费
```

实际报价可能存在：

```text
200 万

300 万

500 万
```

内部统一存储：

```text
2000000
3000000
5000000
```

展示层：

```text
200 万
300 万
500 万
```

---

# 13. 车上人员责任险

必须拆成：

## 驾驶员

字段：

```text
保额

保费
```

例如：

```text
0.1 万

10000 元
```

统一：

```text
10000
```

---

## 乘客

需要额外保存：

```text
单座保额

座位数

总保额

保费
```

例如：

```text
0.1 万 / 座 × 4

或者：

4 座 × 10000 元
```

统一：

```text
单座：
10000

座位：
4

总保额：
40000
```

# 14. 第二层：附加险

真实报价中已经出现多个重要附加险。

---

## 14.1 医保外医疗费用责任险

不能只定义一个：

```text
医保外用药险
```

必须区分保障对象。

至少包含：

### 第三者医保外

```text
THIRD_PARTY_NON_MEDICAL_INSURANCE
```

### 驾驶员医保外

```text
DRIVER_NON_MEDICAL_INSURANCE
```

### 乘客医保外

```text
PASSENGER_NON_MEDICAL_INSURANCE
```

字段：

```text
保险金额

保费

是否共享保额
```

例如实际报价中存在：

```text
30 万

50 万

100 万
```

因此必须可以独立进行比较。

# 15. 外部电网故障损失险

```text
附加外部电网故障损失险
```

需要作为标准附加险维护。

字段：

```text
是否包含

保险金额

保费
```

# 16. 第三层：免费增值服务

不能把：

```text
道路救援
```

当作传统意义上的保险险种。

应该建立：

# ServiceBenefit

统一保存。

目前实际样例已经出现：

```text
道路救援

车辆安全检测

代为驾驶

代为送检
```

字段：

```text
服务类型

服务次数

费用

原始描述
```

例如：

```text
道路救援
2 次
0 元
```

---

# 17. 增值服务详细描述

部分报价单会提供非常长的服务说明。

例如车辆安全检测可能包含：

```text
发动机检测

变速器检测

转向系统检测

底盘检测

轮胎检测

汽车玻璃检测

汽车电子系统检测

车内环境检测
```

第一阶段不需要把这些全部拆成独立字段。

可以保存为：

```text
serviceType

count

description
```

后期再逐渐结构化。

---

# 18. 第四层：独立保障包

这是根据真实报价增加的最重要模块之一。

实际报价中已经出现：

### 人保

```text
途顺家安组合保险

驾乘人员补充综合保险
```

### 平安

```text
平安车主尊享保障
```

这些产品：

**不能与商业车险直接混在一个险种表中。**

原因是它们本质上可能属于：

- 驾乘意外险
- 意外医疗险
- 家财险
- 交通意外险
- 出行保障
- 综合保障产品

因此定义：

# SupplementalPackage

例如：

```text
平安车主尊享保障

价格：
348 元
```

下面再包含：

```text
PackageCoverage[]
```

---

# 19. 独立保障包内部保障

实际报价已经出现：

```text
驾乘意外身故及残疾

驾乘意外医疗

自费医疗

飞机意外

火车意外

轮船意外

汽车意外

救护车费用

个人出行不便

家庭财产保障
```

因此数据应该设计为：

```text
SupplementalPackage

├── Coverage
├── Coverage
├── Coverage
└── Coverage
```

而不是将整包只存成一句：

```text
驾乘险 60 万
```

---

# 20. 特殊保障规则

实际保险方案中还存在：

```text
法定节假日翻倍

每座金额

共享保额

指定人员

不限人员

每次限额
```

因此 Coverage 不能只保存：

```text
amount
```

至少需要：

```text
amount

unit

perSeat

seatCount

shared

multiplier

condition

description
```

例如：

```text
基本保障：
30 万

法定节假日：
翻倍

最终节假日保障：
60 万
```

应该结构化为：

```text
amount = 300000

multiplier = 2

condition = LEGAL_HOLIDAY
```

# 21. 第五层：保险员补充信息

实际报价截图中存在大量：

```text
红色文字

箭头

方框

手写标注

额外宣传语
```

这些内容必须单独处理。

系统需要识别：

```text
PRINTED_OFFICIAL

SALES_ANNOTATION

USER_ANNOTATION
```

即：

### 正式保险公司内容

和：

### 保险员标注内容

不能混为一谈。

# 22. 销售说明识别规则

例如报价图片上出现：

```text
驾乘险 60 万

医保外 50 万

自费医疗

100%赔付
```

系统可以识别出来，但默认状态应该是：

```text
销售补充说明
```

而不是：

```text
正式保险责任
```

UI 中应该明显提示：

> 此信息来自图片附加标注，并非报价单正式表格内容，请用户确认。

# 23. 价格必须重新设计

实际报价证明：

一个简单的：

```text

```

远远不够。

至少需要：

```text

交强险

车船税

额外保障包

其他费用

官方报价总额

优惠

返现

礼品折现金额

最终实付金额
```

# 24. 官方报价总价

例如：

```text
商业险
4392.14

交强险
1045

车船税
0

车主保障
348
```

则：

```text
官方总价：

5785.14
```

系统应该自动重新计算一次。

如果：

```text
系统计算金额
≠
报价单显示金额
```

则显示：

> 金额存在异常，请确认。

---

# 25. 实际成交价

真实保险销售场景中经常存在：

```text
报价 6000

返现 500

微信红包 200

购物卡 100
```

最终真实成本：

```text
5200
```

而这些通常不会出现在正式报价单。

因此报价页面必须允许用户填写：

```text
现金返现

优惠券

红包

购物卡

油卡

其他优惠
```

并计算：

# 实际净支出

公式：

```text
实际净支出
=
（官方报价总额 ?? 系统计算总价）
-
Σ(用户勾选计入、且填写了折现估值的优惠)
```

其他费用已作为价格分项计入总价，不在净支出中单独相加；两个总价皆空时净支出为空。口径详见 `docs/SPEC_MVP.md` 2.2/2.7。

---

# 26. 优惠不能全部简单减钱

例如：

```text
洗车 5 次

保养一次

道路救援

购物卡 200
```

其中：

```text
购物卡
```

可以允许用户填写估值。

但是：

```text
道路救援
```

默认不能直接按照某个金额扣减。

所以权益存在：

```text
cashEquivalent
```

用户可以自己选择是否估值。

---

# 27. 报价单状态值不能简单使用 0

实际报价中存在：

```text
0.00

—

空白

不存在此项目
```

它们的含义可能完全不同。

因此需要状态：

```text
INCLUDED

NOT_INCLUDED

FREE

NOT_APPLICABLE

UNKNOWN
```

例如：

```text
道路救援
2 次
0 元
```

代表：

```text
FREE
```

而不是：

```text
NOT_INCLUDED
```

MVP 状态判断遵循以下原则：明确写有“不投保/无/不包含”才直接记为 NOT_INCLUDED；空白默认 UNKNOWN；“—”只有在所在行列语义明确表示未投保时才记为 NOT_INCLUDED；服务被明确列出且费用为 0 时才记为 FREE。

# 28. 原始数据在项目存续期间必须保留

每一个字段至少保存：

```text
rawName

rawValue

normalizedName

normalizedValue
```

例如：

```json
{
  "rawName": "新能源汽车车第三者责任保险",
  "rawValue": "300万元",
  "normalizedCode": "THIRD_PARTY_LIABILITY",
  "normalizedAmount": 3000000
}
```

这样未来解析算法升级之后，可以重新处理历史报价。

原始报价文件、结构化原始值和字段来源在项目存续期间保留。用户主动删除项目时同步删除数据库记录与本地文件；“保留原始数据”不表示系统可以拒绝用户删除。

# 33. 核心对比页面

核心对比页面采用**单一总表**：全部指标行合并进一张表，方案列横向滑动、相同行折叠（口径见 SPEC §7.2）。

---

# 34. 价格指标

单一总表最上方的价格分组（实际净支出、官方总价、商业车险、交强险、车船税、保障包、其他费用）首先回答：

# 我要付多少钱？

---

# 35. 保障指标

商业四大主险（投保状态、保额、单座保额、座位数、保费）与三者医保外等附加险，作为后续指标行继续排在同一张总表中。

系统自动高亮差异。

---

# 36. 额外保障

独立保障包作为指标行进入同一张总表：保费一行，展开后的内部保障（驾乘身故/伤残、驾乘医疗、自费医疗、节假日保障、家庭财产、交通意外、其他）逐行比较。

---

# 37. 增值服务

道路救援、安全检测、代驾、代办送检等增值服务按类型作为指标行进入同一张总表，逐项比较次数与费用。

---

# 38. 差异优先展示

默认不要让用户自己找差异。

总表中服务端标记的差异行置顶展示并高亮，单元格带 ↑ 增加 / ↓ 减少 / + 新增 / − 缺失 徽标；相同行默认折叠。

「平安 B 比平安 A 贵 365 元」这类结论性说明由第二阶段 AI（§66）回答。

---

# 39. 同公司方案对比

实际使用中非常重要。

项目详情支持按公司筛选报价（只看某家公司），勾选同公司多个方案进入对比，即可在同一张总表中集中比较它们之间的保障与保费差异。

例如选择：

```text

VS

```

系统使用统一 Schema 后进行比较。

# 41. “同口径比较”功能

这是 MVP 对比页必须具备的核心提示能力。

因为：

```text
5000 元方案
```

和：

```text
5500 元方案
```

可能保障完全不同。

系统判断是否具备可直接比较性：

```text
方案 A：
三者 200 万

方案 B：
三者 300 万
```

口径差异直接体现在总表差异行中（集合、状态、保额、单座金额、座位数、共享、倍数、生效条件逐行 ↑/↓/+/−）；任何关键值为 UNKNOWN 时单元格显示「—」并标注，不当 0 比较。

---

# 42. 对比变化标签

推荐使用：

```text
↑ 增加

↓ 减少

+ 新增

- 缺失

= 相同
```

以徽标渲染在单元格文本旁，基准列不标箭头。

两个方案按用户勾选顺序，以第一个为基准；三个及以上方案仍固定使用第一个为差异基准，并在页面明确标注。

总表本身已给出价格分项与各险种保费行；数据不足的单元格显示「—」，不做猜测性归因。

# 46. 第二阶段首批 AI 能力

# 47. AI 推荐必须谨慎

产品定位建议为：

# 决策辅助

而不是：

# AI 替用户买保险

所以 AI 不应该简单回答：

```text
你应该买方案 A。
```

应该回答：

```text
如果你最关注总价格，
A 成本最低。

如果你希望三者险达到 300 万，
B 和 C 满足条件。

如果你更关注医保外第三者保障，
A 的额度更高。

如果你希望同时拥有额外驾乘保障，
C 包含独立保障包。
```

最终决定交给用户。


# 49. 隐私设计

真实报价单包含大量敏感信息，例如：

```text
车主姓名

车牌号

车架号

发动机号

身份证相关信息

手机号
```

但是绝大部分：

# 与报价对比无关。

因此应该采用数据最小化原则。

例如系统可以保存：

```text
车型

座位数

初登日期

是否新能源
```

而：

```text
姓名

完整车牌

VIN

发动机号
```

默认：

### 不采集、不入库。

模型输出白名单只允许车型、座位数、初登日期、是否新能源；姓名、完整车牌、VIN、发动机号不返回、不存储（详见 `docs/SPEC_MVP.md` §9）。

隐私边界必须明确：报价原图会发送至用户当前配置的第三方视觉模型进行推理，因此首次解析前必须告知传输目的并取得确认；“文件只存本地”不等于“文件不会发送给模型”。用户拒绝时仍可使用手动录入。

模型输出白名单不能作为唯一保护。后端还必须对来源摘录、销售说明、未识别文本和错误日志进行脱敏；默认仅允许本机访问，开放到局域网时启用轻量访问令牌。原文件通过受控接口查看，不得作为公开静态文件暴露。

# 59. 自动校验规则

系统至少实现：

## 总金额校验

```text
商业险
+
交强险
+
车船税
+
独立保障
≈
报价总额
```

校验结果必须区分：PASSED（通过）、MISMATCH（不一致）、NOT_CHECKABLE（分项不足，无法校验）。任何空值都不能被系统自行当作 0；用户明确确认“不包含”后才按 0 参与计算。

---

## 保额单位校验

例如：

```text
300万元
```

必须转换：

```text
3000000
```

---

## 座位校验

例如：

```text
0.1万元/座 × 4
```

解析：

```text
perSeat = 1000

seatCount = 4
```

---

## 重复险种校验

防止：

```text
三者险
```

被解析模型重复提取。

只有原始名称、原始值、金额和来源完全相同的行可以自动去重。同一标准险种出现不同保额、保费或来源时不得静默丢弃，必须交给用户确认。

---

## 主险 / 保障包隔离校验

例如：

```text
驾乘意外 30 万
```

来自：

```text
车主尊享保障
```

则不能错误覆盖：

```text
车上人员责任险驾驶员
1 万
```

这两个保障完全不是同一个东西。

```text
+

不同保险公司报价模板库

+

```

随着真实报价越来越多：

> 一张保险公司报价单到底应该怎么看。

# 69. 产品核心原则

整个产品建议始终坚持一个原则：

# 原始数据与标准数据并存。

数据库不能只保存：

```text
三者险
300万
```

而必须同时保留：

```text
原始报价：
新能源汽车车第三者责任保险

原始值：
3000000.00元

标准险种：
第三者责任险

标准保额：
3000000

来源：
报价单第1页

置信度：
98%
```

这是未来整个系统能够持续优化的基础。

# 70. 最重要的产品调整

结合实际报价以后，这个产品不应该定义成：

> 图像识别车险报价然后做表格。

正确的产品定义应该是：

# 多保险公司车险报价标准化与决策辅助系统

它实际上做的是：

```text
不同保险公司的报价语言
            ↓
统一保险数据语言
            ↓
形成真正可比较的数据
```

整个系统最核心的三个引擎分别是：

```text
① Quote Parser
报价解析引擎

② Insurance Normalization Engine
保险字段归一化引擎

③ Comparison Engine
报价比较引擎
```

以后增加：

```text
④ Insurance Analysis Agent
保险分析 Agent
```

形成：

```text
报价单
  ↓
Parser
  ↓
Normalization
  ↓
Comparison
  ↓
AI Agent
```

这会比单纯做一个“上传图片 → GPT 分析”的产品稳定得多，也更容易形成长期技术和数据壁垒。

# 71. 第一版成功标准

MVP 不需要做到所有保险公司的所有险种都能识别。

第一阶段可以先要求：

### 人保 + 平安

两家公司支持度最高。

针对真实车险报价，至少做到：

- 核心险种识别准确；
- 三者 200 万 / 300 万能够正确区别；
- 司机、乘客责任险不会混淆；
- 医保外第三者 / 驾驶员 / 乘客不会混淆；
- 独立驾乘保障不会错误归类为车上人员责任险；
- 0 元服务能够识别为“免费”，而不是“不包含”；
- 额外保障包能够独立计算价格；
- 官方总价能够自动校验；
- 红色文字、箭头等销售员备注不会自动污染正式保单数据；
- 用户能够修改任何 AI 识别错误的数据；
- 任意两个方案能够快速看到价格和保障差异。

上述“准确、稳定、快速”按 `docs/SPEC_MVP.md` 第 15 节验收：使用 10 份脱敏标注报价（人保、平安各不少于 5 份），核心字段完全正确率至少 95%；司机/乘客互换、三个医保外对象互换、保障包污染主险、销售标注污染正式字段等高风险错误必须为 0。拆分、手动录入、补传合并、导出各验证 1 条端到端主路径，不要求建立大规模测试矩阵。

如果这十项能够稳定做到，这个产品的 MVP 已经具备非常明确的实际使用价值。
